# 🧪 FME Integration Test Suite: Validation and Usage Guide

This documentation covers the usage and architecture of the **Integration Test Suite** located in the `INTEGRATION_TESTS` directory.
This suite is the **ultimate gatekeeper**, ensuring **byte-for-byte fidelity** between different FME versions of the final metadata output.

---

## ⚙️ 1. Prerequisites and Execution Environment

The entire testing framework is **year-agnostic** and requires two specific FME installations to be installed locally.

### A. Environment Setup (Mandatory)

Before running any test script, you must set two **permanent system environment variables**:

| Environment Variable | Target FME Version | Purpose                                                | Example Path                                  |
| -------------------- | ------------------ | ------------------------------------------------------ | --------------------------------------------- |
| `FME2020`            | 2020.2 Production  | Points to the stable production executable (baseline). | `C:\Program Files\FME\fme-form2020\fme.exe`   |
| `FME2025`            | 2025.1 Upgraded    | Points to the newly upgraded executable.               | `C:\Program Files\FME\fme-form2025.1\fme.exe` |

---

### B. Canonical Test Data (`ETALON_DATA`)

The tests rely on a dedicated directory structure which mimics the required staging/production environment data path (`C:\data\pt_harvester`):

* **Location:** `INTEGRATION_TESTS\ETALON_DATA`
* **Contents:** Contains the sample FFS input files (e.g., `AB_sample.ffs`) and the expected canonical outputs (`.xml`, `.json`) generated by the FME 2020 production environment.
* **Critical Feature:** Each FFS file includes **exactly 3 GEO features** and **3 NON-GEO features**, guaranteeing that both **geometry** and **non-geometry** publishing logic (XML/JSON pipelines) are exercised during every test run.

---

## 🚀 2. Running the Integration Tests

The test suite is controlled by **simple batch files** designed for immediate execution from the command line.

### A. Master Test Scripts

These scripts, located in the root of the `INTEGRATION_TESTS` folder, perform comprehensive validation across all provincial workspaces.

| Script Name                 | Purpose                                                                                                                                                                                    | Execution                   |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------- |
| `run_all_2020_AND_2025.bat` | **Primary Validation.** Executes every workspace twice (once with FME 2020 and once with FME 2025) and compares both outputs to the `ETALON_DATA`. This is the definitive migration check. | `run_all_2020_AND_2025.bat` |
| `run_all_tests_2025.bat`    | **2025 Regression Check.** Runs all workspaces using FME 2025 only. Useful for daily CI/CD checks on the upgraded code base.                                                               | `run_all_tests_2025.bat`    |
| `run_all_tests_2020.bat`    | **2020 Baseline Check.** Runs all workspaces using FME 2020 only. Confirms that the old production code still aligns with the `ETALON_DATA`.                                               | `run_all_tests_2020.bat`    |

## 🧠 3. Integration Test Architecture Explained

The test suite achieves its **year-agnostic functionality** and **definitive comparison** through a layered, clean-room approach.

---

### A. The Core Runner (`INTEGRATIONTEST.bat`)

This single script handles the execution logic for any FME version.

1. **Dynamic FME Path**
   The master scripts pass the target executable (e.g., `%FME2025%`) through the dynamic variable `FME_EXECUTABLE`.

2. **Workspace Execution**
   Calls the target `.fmw` workspace via `%FME_EXECUTABLE% path/to/workspace.fmw`.
   The workspace generates `RESULTAT` XML and JSON files in a temporary directory.

3. **Comparison Phase**
   Executes the two key comparison workbenches:

   * `Comparateur_XML.fmw`
   * `Comparateur_JSON.fmw`

4. **Comparison Logic**
   The comparison workbenches read both the **official ETALON** file and the **generated RESULTAT** file.
   They use **ChangeDetectors** with custom Comparator logic to classify each feature as `UNCHANGED`, `UPDATED`, `DELETED`, or `INSERTED`.

5. **Final Verdict**
   The runner reports:

   ```
   SUCCESS: All tests passed
   ```

   only when **zero differences** are detected across both XML and JSON comparisons.

---

### B. Comparison Workspaces

`Comparateur_XML.fmw` / `Comparateur_JSON.fmw`

These workbenches are engineered to eliminate **FME version noise** through attribute normalization and deterministic processing.

| Transformer                          | Purpose in Comparator                                                                                           | Rationale                                                                                       |
| ------------------------------------ | --------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| **JSONFlattener / XMLFlattener**     | Explodes ETALON and RESULTAT files into atomic attribute-value pairs.                                           | Enables line-by-line, attribute-by-attribute comparison of metadata content.                    |
| **ListSorter / Aggregator / Sorter** | Re-sorts list and nested attributes on both ETALON and RESULTAT streams using stable keys (e.g., `_signature`). | Stabilizes order of attributes that FME 2025 may randomize (`distributionInfo`, `resources{}`). |
| **ChangeDetector**                   | Compares the flattened ETALON (Original) and RESULTAT (Revised) features.                                       | Detects whether each feature is `UNCHANGED`, `UPDATED`, `INSERTED`, or `DELETED`.               |
| **Terminator**                       | Allows only `UNCHANGED` features to pass.                                                                       | Stops translation immediately on any detected difference and logs the test as **FAILED**.       |

This ensures the comparison remains **semantic** (data integrity and feature equivalence), not merely **structural**, ignoring safe, non-critical version differences.

## 🧰 4. Tools for Maintenance

To simplify ongoing maintenance and debugging, the following supporting Python scripts are included:

| Script Name                              | Category         | Primary Use                                                                                         |
| ---------------------------------------- | ---------------- | --------------------------------------------------------------------------------------------------- |
| `create_ffs_subsamples_w_geo_non-geo.py` | Data Preparation | Generates new `ETALON_DATA` samples by selecting 3 GEO and 3 NON-GEO records from a full FFS input. |
| `unit_tests_runner.py`                   | Unit Testing     | Automates individual custom transformer test runs against FME 2020 and FME 2025.                    |
| `fme_workspace_vs_unit_test_report.py`   | Test Coverage    | Audits production workspaces, mapping transformer usage and identifying missing test harnesses.     |
